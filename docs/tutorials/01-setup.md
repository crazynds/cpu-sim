# 1. Setup and measurement hygiene

## Requirements

The simulator runs CUDA kernels on AVX-512 vector lanes, so the CPU must have AVX-512. What each feature needs:

| Feature | Instruction sets | CUDA equivalent |
|---|---|---|
| Any kernel (the device refuses to start without these) | AVX-512 F, BW, DQ, VL; FMA | the device itself |
| `half` and `__nv_bfloat16` arithmetic (`cuda_fp16.h`, `cuda_bf16.h`) | same as above (computed in fp32, rounded as CUDA does) | |
| WMMA with `half` inputs | F16C + FMA (present on every AVX-512 CPU) | compute capability 7.0 |
| WMMA with `signed char` / `unsigned char` inputs, and the experimental 4-bit and 1-bit types | AVX512-VNNI (`vpdpbusd`) + AVX512-VBMI (byte permutes) + AVX512-VPOPCNTDQ (`vpopcntd`) | compute capability 7.5 |
| WMMA with `__nv_bfloat16`, tf32 or `double` inputs | AVX512-BF16 (`vdpbf16ps`), in addition to the above | compute capability 12.0 (these kernels need 8.0) |

The device reports the highest compute capability its CPU supports; a kernel that needs a higher one fails to launch with `cudaErrorNoKernelImageForDevice`, as on an older GPU. Check what yours has:

```sh
grep -o 'avx512[a-z_0-9]*' /proc/cpuinfo | sort -u
```

The device code is compiled for the CPU it is compiled on (`-mcpu=native`, both in `cucc` and in the JIT at run time), so it uses whatever extensions that CPU has. To build a binary for another machine, pass `--mcpu=<cpu>` to `cucc` (for example `--mcpu=znver4`, `--mcpu=sapphirerapids`).

Also needed: GCC 13+, CMake 3.24+, LLVM/Clang 19 (setup in the [README](../../README.md#build)), and for the GPU comparisons `nvcc` with cuBLAS. Without a GPU, skip the GPU commands.

## Build and test

Every command in these tutorials runs from the repository root, and the benchmark programs are built into `build/bench/` (ignored by git):

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
mkdir -p build/bench
```

CMake may print `Could NOT find FFI / LibEdit / zstd / LibXml2 / CURL`: those are optional dependencies that LLVM's CMake package probes for, and the project does not use them. What matters is the `LLVM 19.x.x: <path>` line and `Configuring done`.

Use `Release` (`-O3`) for benchmarks. The project's default, `RelWithDebInfo` (`-O2 -g`), is for development: the symbols let `perf` and `gdb` map back to the source. The build type only affects the code GCC compiles (the compiler, the runtime and the executor); the kernels are generated by `cpusim-devc` with `-O3` in either case.

Every test must pass before measuring anything: a benchmark of a compiler that miscompiles is meaningless.

## Start the device

The driver, `cpusimd`, owns the device: it decides which CPUs run the kernels (the "multiprocessors"), reserves the simulated VRAM, and serves every CUDA program. Programs only talk to it through the CUDA API.

```sh
build/cpusimd --daemon
build/cpu-smi -q
```

`cpu-smi -q` shows the device: compute capability, tensor core types, the number of multiprocessors (physical cores) and which logical CPUs they are.

The configuration file, `~/.config/cpusim/device.toml`, is optional: without it (`Config : (defaults)` in `cpu-smi -q`) the driver takes every physical core but the first two, with their SMT siblings, and sizes the VRAM from the RAM. To change anything, generate the file with this machine's defaults, all commented out, and uncomment what you want:

```sh
build/cpusimd --init-config        # writes ~/.config/cpusim/device.toml; never overwrites
```

The keys that matter for benchmarks are `cores` (how many physical cores) and `cpus` (which ones). Restart the driver after editing.

After rebuilding the project, restart the driver so it runs the new build:

```sh
build/cpusimd --stop && build/cpusimd --daemon
```

Without a running driver, programs run the device inside their own process (the in-process backend), with the same configuration. Kernel times are the same either way (the driver only adds a little latency per launch); the tutorials use the driver because `cpu-smi` needs it.

## Watching the device

Like `nvidia-smi` on a GPU, keep `cpu-smi` running in a second terminal while benchmarking:

```sh
build/cpu-smi --query-gpu=temperature.gpu,clocks.sm,utilization.gpu --format=csv -l 0.5
```

`clocks.sm` is the mean current clock of the device's CPUs, from cpufreq; `temperature.gpu` is the CPU temperature; `utilization.gpu` is the fraction of time a kernel is running.

## Getting stable numbers

A CPU running AVX-512 on all cores is limited by power and temperature: the clock it holds depends on the cooling and on how hot it already is, and two runs of the same binary minutes apart can differ by tens of percent on a thermally constrained machine. So:

1. **Idle system.** Close other heavy programs; check with `top`.
2. **Watch `cpu-smi`** during the runs: if the clock drops between two runs, their numbers are not comparable.
3. **Pause between runs** and **compare in pairs**: run the two contenders back to back, alternate which goes first, and compare the ratio within each pair rather than numbers taken minutes apart. `bench/gemm_duel.sh` does exactly this.
4. **Measure the ceiling in the same state** (tutorial 2): an efficiency is only meaningful against the peak measured right before.
5. **OpenMP next to CUDA:** a program that also runs OpenMP code (the benchmarks' `omp` references) should set `OMP_WAIT_POLICY=passive`. By default libgomp's threads keep spinning for milliseconds after each parallel region, on every CPU, the device's included, and a kernel launched in that window shares its workers' CPUs with them.

## First run of a CUDA program

Each block shape runs code specialized for it. `cucc` compiles it ahead of time for the shapes that are constants at the launches in the source; a launch with any other shape compiles it then (JIT, cached in `~/.cache/cpusim/jit`), which takes seconds on the first run. The first launches also choose the lane width by measurement. All benchmarks here do an untimed warm-up for both reasons. `CPUSIM_VERBOSE=1` shows which shapes came ready and which went through the JIT.
